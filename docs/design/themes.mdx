Every widget widgentic renders is styled through `wg-*` classes and `--wg-*` custom properties. A theme is a validated JSON map of those tokens. The theme designer, in the app under **Themes** or embedded in your own page, edits a named theme entry, validates every value, and previews it against the built-in kinds and your own widgets. The full token table lives in the [Theme tokens reference](/reference/theme-tokens).

## The theme entry

A theme is one JSON object, `{ name, label?, description?, tokens, styles? }`. `tokens` maps bare token names (no `--wg-` prefix) and `x-*` custom variables to string values; `styles` holds shared classes (see [Shared styles](#shared-styles)).

```json
{
  "name": "brand",
  "label": "Brand",
  "tokens": {
    "bg": "#0b0e14",
    "accent": "#ff5a1f",
    "font-family": "Inter, sans-serif",
    "x-badge-gap": "4px"
  }
}
```

`name` follows the identifier charset `^[a-zA-Z0-9._-]+$`. `light` and `dark` are reserved for the built-in entries; saving a theme under either name is refused with `RESERVED_THEME`.

## Registry tokens

Each registry token declares a `type` (`color`, `dimension`, `number`, `font-family`, `font-weight` or `shadow`), a documented `use`, and a light default. The registry covers surfaces and text (`bg`, `surface`, `fg`, `muted`), the accent pair (`accent`, `accent-fg`), borders and radii (`border`, `border-width`, `radius`, `radius-sm`, `radius-lg`), the spacing scale (`spacing`, `spacing-sm`, `spacing-lg`), typography (`font-family`, `font-mono`, `font-size`, `font-size-sm`, `font-size-lg`, `font-weight-bold`, `line-height`), `shadow`, the status families (`danger`, `success`, `warning`, `info`, each with a `-fg` text color), and the image sizes `avatar-size` and `thumb-size`.

The designer renders one control per token, chosen from its declared type: `color` tokens get a picker and a swatch of the effective value, and each token's `use` appears as help text. Every token is consumed by the base stylesheet; a token nothing uses is not added to the registry.

A theme sets only what it changes. Tokens you omit keep their defaults, and `surface` inherits `bg` unless you set it, so a theme that sets only `bg` colors widget surfaces with that value.

## Custom variables

Keys matching `^x-[a-z0-9][a-z0-9-]*$` are author-defined custom variables. `x-badge-gap` is applied as `--wg-x-badge-gap` on the themed scope, and a widget's styles read it as `var(--wg-x-badge-gap, 4px)`. Give custom variables a fallback: they are defined only by themes that set them, whereas every registry token is always defined at render time, so a bare `var(--wg-spacing-lg)` is safe.

The designer lets you add, rename and remove custom variables; they appear in the exported entry's `tokens` beside the registry tokens.

## Shared styles

A theme can also define **styles**: rules for `.wg-` classes that any widget rendered under the theme can use, so a look shared by many widgets is written once. The shape is the same as a widget's own styles: selectors mapping to property/value pairs.

```json
{
  "name": "brand",
  "tokens": { "accent": "#ff5a1f" },
  "styles": {
    ".wg-btn": { "padding": "4px 10px", "border-radius": "var(--wg-radius)", "background": "var(--wg-accent)", "color": "var(--wg-accent-fg)" },
    ".wg-badge-ok": { "background": "var(--wg-success)", "color": "var(--wg-success-fg)" }
  }
}
```

A widget's template then uses the class (`{ "tag": "button", "attrs": { "class": "wg-btn" } }`) and gets the theme's look wherever the theme applies. The rules are the widget rules. Each selector part (split on top-level commas) must be held to `.wg-` classes: one of its compounds names a `.wg-` class itself, or through `:is()` or `:where()` whose every argument does, as in `.wg-card .wg-xcard-head`, `.wg-row:has(.wg-ok, .wg-warn)` or `:is(.wg-btn, .wg-link):hover`. A `.wg-` class only inside `:not()`, `:has()`, an attribute test or a string does not count, and a part may not open with a combinator. Selectors, properties or values containing `;`, braces, `<`, `>`, `@`, a backslash, a comment marker (`/*` or `*/`) or an unclosed bracket or string are dropped, as are values calling `url(`, `expression(`, `image-set(` or `src(`, and property names outside letters and hyphens. A theme's styles are emitted before the rendered widget's own styles, so a widget can always override a shared rule.

The theme designer edits styles with the widget designer's own Styles panel, with the same Tree and JSON tabs and the same warnings for entries that would be dropped. The preview shows them on every kind you select. In the widget designer, choosing a preview theme applies its styles too, so a shared class looks in your draft as it will in a render. Agents see a theme's styles in `list_themes`.

## Value safety

Values are plain CSS values: colors, lengths, font stacks. A value that is not a string, that contains `;`, `{`, `}`, `<`, `>`, a backslash, a comment marker (`/*` or `*/`) or an unclosed bracket or string, or that calls `url(`, `expression(`, `image-set(` or `src(` (case-insensitive, whitespace-tolerant before the parenthesis), fails with `INVALID_TOKEN_VALUE`, custom variables included. A key outside the registry that is not a valid `x-*` name fails with `UNKNOWN_TOKEN`. The guard rejects exfiltration and execution vectors, not invalid CSS: an inert nonsense value passes.

In the designer an unsafe value is flagged inline with the validator's error and excluded from the applied preview, so the preview never shows a theme the server would refuse. The store refuses such a value on write. On read, a stored value the rule refuses, such as one saved under looser rules, is dropped with a diagnostic and the rest of the theme is kept.

## Light defaults and the dark preset

Two entries exist in every catalog. `light` is the empty token map, which means the registry defaults. `dark` is the built-in dark preset; it sets `surface` to a value distinct from `bg`. When you press **New** in the app you can start from either: the designer seeds a copy of the preset's tokens under a distinct, non-reserved name.

## Default themes

When a render names no theme, hosts fall back to the built-in look: the light defaults on light hosts and the dark preset on dark ones. In **Settings → Default themes** you can choose your own theme for each: one for light hosts, one for dark hosts, or the same theme for both. Each mode holds one choice, so picking a theme replaces the previous default for that mode. Choosing the built-in again clears it.

Your choice applies to every render that names no theme, for all your keys. On a host in dark mode the dark default's tokens apply; elsewhere the light default's do. Shared styles follow the same split only when both modes' defaults carry styles; otherwise a default's styles apply in both modes, since widgets rely on those classes for layout. One theme chosen for both modes applies in both, tokens and styles, as a named theme does. Documents with no host colour scheme (`format: "page"` and `"app"`) use the light default. A render that names a theme still uses that theme. A default theme overrides the host's own colours in its mode, as a named theme does.

A theme that is a default cannot be deleted; the app answers `THEME_IN_USE` until you choose another default. `list_themes` reports the current defaults to agents. Settings are not part of the theme entry, so exporting or importing a theme never changes your defaults.

## Previewing

In the app the theme preview runs in the same frame as the widget designer's, the document hosts mount (see [Widget designer](/design/widget-designer#sample-data-and-preview)). The preview-kind selector offers the built-in kinds and, in the app, your own stored widgets, each rendered from its `dataExample` with its descriptor styles applied, so the theme is judged against the widgets it will actually dress. A stored widget whose template fails validation is skipped; the rest stay selectable. Token edits preview immediately.

The widget designer runs the other direction: your saved themes appear in its preview-theme selector, with a read-only token reference showing the effective values. See [Widget designer](/design/widget-designer).

## Import, export and saving

Import and Export are independent sections, Import first. Import accepts the entry shape above, re-validates it, and rejects an entry whose tokens fail without replacing the working entry; an exported entry re-imports deep-equal.

In the app, saving publishes: the theme appears in `list_themes` for your keys and can be passed to `render_widget` as `theme: "brand"`. Pass the **name**, not the token map. Your saved theme is the server-side source of truth, and a reconstructed map drifts the moment you edit it. Agents draft themes from `list_theme_tokens` and the authoring guide; see [Authoring with an agent](/design/authoring-with-an-agent).
