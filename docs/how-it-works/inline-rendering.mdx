title: "Inline rendering in MCP Apps hosts"
description: "How render_widget results become widgets inside the conversation, and what hosts without MCP Apps receive instead."

Hosts that implement MCP Apps can display a widget inline in the chat. widgentic follows the official convention (spec version `2026-01-26`, through `@modelcontextprotocol/ext-apps`) and keeps a text path for every other host.

## The app template

`render_widget` is registered with `_meta.ui.resourceUri` pointing at `ui://widgentic/app.html`. That resource is served with mime type `text/html;profile=mcp-app` and is a self-contained document: the widgentic base stylesheet plus a small inline bridge implementing the iframe side of the protocol — the `ui/initialize` handshake, the `ui/notifications/initialized` notification, `ping` and `ui/resource-teardown` responders, and `ui/notifications/size-changed` reports. It references no external resources and contains no imports, so the strictest sandbox a host offers is enough. Its `_meta.ui`, on the resource declaration and on the read content alike, carries `prefersBorder: false`, since widgets draw their own surface, and `csp.resourceDomains` only when the operator or the person has declared [resource domains](#resource-domains).

The host mounts it in a sandboxed iframe; `buildAppTemplate()` from `@widgentic/mcp` produces the same document for anyone running their own server.

## What each render sends

Every successful `render_widget` result, whatever `format` was requested, carries `structuredContent`:

```json
{
  "html": "<div class=\"wg-card\">...</div>",
  "css": ".wg-invoice { border: 1px solid var(--wg-border) } :root, :root[data-theme=\"dark\"] { --wg-accent: #ff5a1f; }",
  "payload": { "kind": "invoice", "data": { "lines": [] }, "theme": { "accent": "#ff5a1f" } },
  "tree": { "tag": "div", "attrs": { "class": "wg-card" }, "children": [] }
}
```

- `tree` is the render tree and `html` its serialization: two projections of one render, never divergent.
- `css` holds the theme's shared styles, then the registered styles of the kind (for a `group`, every item kind's styles exactly once), then the theme's token declarations. When no `theme` is named, the caller's [default themes](/design/themes#default-themes) take its place, scoped per mode.
- `payload` is the validated payload, carrying the resolved `theme` as a top-level field when one was given.
- `diagnostics` appears only when hint analysis found something; `load` (or `loads` for a group) appears only when the kind declares a load binding and the caller holds the `execute` scope.

The bridge listens for `ui/notifications/tool-result` and mounts the tree natively: DOM built with `createElement` and `createTextNode`, tag and attribute names held to the serializer's allowlists, `on*` attributes skipped. When a later result has the same shape, the existing DOM is patched in place and the root element object survives. Sibling lists whose elements all carry a distinct `key` — table rows and tree nodes with record `id`s, template `each` lists with a `key` path — are paired by key, so a result that reorders them moves the existing elements and a branch the reader opened stays open; any other list is paired by position. The `html` fragment is injected into the root only when `tree` is absent.

Three more bridge behaviours:

- **Streaming preview.** On `ui/notifications/tool-input-partial`, built-in kinds (and groups of built-ins) are previewed in the frame from the partial input, marked in progress and patched as more arrives, applying `hints.labels`, table `hints.columns` and card `hints.fields` as the renderers do. A stored widget, alone or inside a group, shows a skeleton naming the kind; when the host proxies tool calls (`serverTools`), the frame asks the server for a preview through the app-only `preview_widget` tool and shows the answer instead. The frame acts on a widget name only once it has fully arrived, so it never asks about a half-streamed name or mistakes one for a built-in; until then it shows an unnamed placeholder. Agents are asked to write `widget` first and any `hints` before `data`, so a preview shows labels, columns, field order and image places from the first row. One request is in flight at a time, the latest input goes next, and any failure keeps the skeleton. Previews never show an image's URL: wherever the result will draw an image, a box of the same shape holds its place, and a URL still arriving is left out until it is complete. The frame never guesses a render. The tool result replaces the preview, images included.
- **Themed previews.** The frame builds built-in previews itself, but the caller's default themes live on the server. Once a built-in kind's name settles, and when the host proxies tool calls, the frame calls `preview_widget` with only `{ widget, theme? }` (a group as `{ widget: "group", data: { items: [] } }`) and applies the CSS it answers: the caller's default themes, or the named theme once it has fully arrived. It asks again only when a different theme settles, and an answer that arrives after the tool result is discarded.
- **Host context.** The host's theme is applied as `data-theme` and `color-scheme`, its style variables flow into the `--wg-*` tokens, and safe-area insets become body padding. When the host theme is dark, the tokens the bridge does not map follow the dark preset, except those the caller's dark default theme sets; a default theme in its mode, like an explicit widgentic `theme`, wins over the host's values. Anchor clicks never navigate the frame: the template asks the host to open `http(s)`, `mailto` and `tel` links through `ui/open-link`.

## Formats

`format` picks which content blocks travel; the render itself does not change.

| Value | Content | Use it for |
|---|---|---|
| `both` (default) | HTML fragment text block plus the widgentic payload block (`application/vnd.widgentic+json`) | Any host; Apps hosts mount from `structuredContent` |
| `html` | The fragment only | Embedding the markup yourself |
| `widget` | The payload block only | Natively mounting hosts |
| `page` | A self-contained styled document (`<!doctype html>`, inlined base stylesheet, theme declarations, kind styles, body coloured from the tokens) plus the payload block | Opening in a browser |
| `app` | A one-line text fallback, a `text/html;profile=mcp-app` resource at `ui://widgentic/page/<kind>` holding that same styled page, and the payload block | Legacy embedded-resource hosts (mcp-ui lineage) |

An unrecognized value returns `INVALID_TYPE` at `path: "format"`.

## Hosts without Apps support

A client that does not advertise the Apps capability (`extensions["io.modelcontextprotocol/ui"]`) gets the same tools with the template simply unmounted: the HTML text block and payload block, or a `page` document to open in a browser. Claude Code is the everyday case: its tool results are text and it does not mount MCP Apps UI by design. Hosts that understand the widgentic mime type can mount the payload block natively with `extractWidgetPayload` and `@widgentic/core`; see [Render in your host](/develop/render-in-your-host).

## Model-context slimming

In an Apps host the person already sees the widget, so the model does not need the markup. The default-format result replaces the full-HTML text block with a one-line confirmation naming the kind, stating that the visual is already displayed and instructing the model not to restate the data. The payload block and `structuredContent` are unchanged, and the `Hint notes:` and `Action notes:` tails still reach the model. The signal is the client's UI capability: negotiated once by a 2025-era session, or carried in every 2026-07-28 request's `_meta`. `WIDGENTIC_ASSUME_UI=1` covers calls that reveal neither, such as stateless 2025-era HTTP. Explicit formats are never slimmed.

## Script-free, network-free content

Widget content contains no scripts and no external references; the only stylesheets a frame links are the ones a person lists in Settings ([Stylesheets](#stylesheets)). That is by construction — the render tree cannot emit raw HTML, templates reject `script`, `iframe`, `style`, `link` and the other active-content tags, and theme values cannot call `url(`, `image-set(` or `src(`.

The one external reference a widget can legitimately carry is an image source, and Apps sandboxes block external `img-src` while permitting `data:`. The server therefore inlines images on the iframe-facing surfaces — `structuredContent.html`, `structuredContent.tree` and the `ui://widgentic/page/<kind>` resource — turning each `https` source whose guarded fetch succeeds into a `data:` URI. The fetch refuses private, loopback, link-local and metadata addresses, requires an `image/*` content type, caps each image at 1 MiB and about 4 seconds, and fetches at most 24 sources per render in priority order: card heroes first, then thumbnails, avatars and template images, then tree icons. Fetched sources are admitted while the bytes they substitute fit 3 MiB per render, where a source used by 200 nodes is charged 200 times; a source that does not fit keeps its URL, and a smaller one after it may still be inlined. A failure or an overflow leaves the original URL and its alt text. The model-facing HTML text block and `page` output keep the original URLs. Domains declared as [resource domains](#resource-domains) (the operator's, then the person's from Settings) go out as canonical origins in `_meta.ui.csp.resourceDomains`, and hosts that honor them load images from them directly. Sources on them rank after every undeclared source, because inlining is the only route the undeclared ones have, so a declared image is inlined only with the room left over and otherwise keeps its URL. The stderr note counts declared leftovers separately. `WIDGENTIC_INLINE_IMAGES=0` disables inlining. Per-host behaviour is in the [Host matrix](/how-it-works/host-matrix).

## Resource domains

In **Settings → Resource domains** a person lists the domains their frames may load images from directly. An entry is a host, `cdn.example.com`, or a wildcard, `*.example.com`, optionally behind `https://`; case is ignored and the entry is saved in its canonical `https://` form. A wildcard covers subdomains at any depth but never the apex: `*.example.com` matches `a.example.com` and `a.b.example.com`, not `example.com`. A person's list holds at most 20 entries.

The rule refuses, naming the entry (`INVALID_DOMAIN`): any scheme but `https://`, a port, a path, a query, a user name, an IP address, a single-label name, a `localhost` name, and a wildcard anywhere but the whole first label. A non-ASCII name is entered in its punycode (`xn--`) form.

The operator's list comes first, then the person's, duplicates dropped. Declared sources are inlined last, so past the inlining caps they keep their URL and a host honoring the declaration loads them directly. Stored widgets and render inputs cannot add a domain; what declaring one exposes is in the [Trust model](/how-it-works/trust-model).

## Stylesheets

In **Settings → Stylesheets** a person lists up to 8 stylesheets every frame of their widgets links: an icon font such as `https://fonts.googleapis.com/icon?family=Material+Icons`, or a brand font. An entry is an `https://` address on a host, with no port or user name, optionally pinned by a Subresource Integrity value (`sha256-`, `sha384-` or `sha512-` followed by base64).
- **Its domain must be declared.** The stylesheet's host must be one of the person's resource domains, or the save is refused with `UNDECLARED_DOMAIN`. That includes a save that removes a domain a stylesheet still needs. A stylesheet's fonts come from their own domain, which must be listed too: `fonts.gstatic.com` for Google Fonts.
- **Delivery.** The stylesheets ride every render, preview and action result as `structuredContent.resources`. The app template keeps one `<link rel="stylesheet">` per entry, before the widget's CSS so the theme's and widget's own rules win a tie. It keeps a link across results without reloading it.
- **Where they never go.** `page` documents link them in their head. The `html` fragment and the payload block never carry them, because a host places those in its own page.
- **The server's check.** It delivers only stylesheets the declared domains (the operator's, then the person's) cover, so a host never sees a link its policy would block.
- **Classes in templates.** `list_themes` lists the stylesheets, so an agent drafting a template knows that, say, `material-icons` is available. A template uses a stylesheet's classes like any other: `{ "tag": "span", "attrs": { "class": "material-icons" }, "children": ["mail"] }`.
- **Pinning.** An integrity value pins a stylesheet that must not change. Google Fonts serves different CSS per browser, so it cannot be pinned.
- **Host policy cache.** claude.ai keeps a declared policy for the page session, so reload the page after adding a domain.

Stylesheets can do anything CSS can inside the frame; what that exposes is in the [Trust model](/how-it-works/trust-model). Scripts and web components are not supported.
