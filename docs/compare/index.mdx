## Three layers, not one race

The field has settled on a vocabulary that keeps most of these projects from competing head-on. CopilotKit states it as *generation → transport → rendering*; the OpenUI "State of Generative UI" report splits the same thing into a **transport** decision (where the UI appears) and a **generation** decision (what the agent emits).

| Layer | Question | Projects |
|---|---|---|
| Transport | How does an agent's output reach a surface a person sees? | **MCP** tool results and **MCP Apps** (third-party hosts: ChatGPT, claude.ai, VS Code, Goose, Postman); **AG-UI** (an application you own); **A2A** (agent to agent, with A2UI as an extension) |
| Generation | What does the agent emit? | *Static / registry*: a kind plus data (**widgentic**, CopilotKit tool renders). *Declarative*: a component tree from a catalog (**A2UI**, **Open-JSON-UI**, **json-render**, **OpenUI Lang**). *Open-ended*: HTML/JS the model wrote (raw **MCP Apps** and **OpenAI Apps SDK** resources) |
| Rendering | Who turns the emitted thing into pixels? | The host's sandboxed iframe (MCP Apps, Apps SDK); the application's own components (AG-UI + CopilotKit, A2UI renderers); a shipped-in renderer (**widgentic**'s app template, A2UI's "renderer inside an MCP App" pattern) |

widgentic occupies **generation and rendering** and rides on **MCP** for transport. It is the only project in the table that is simultaneously a registry-style payload contract, a people-authored declarative template layer, a renderer that ships itself into hosts it does not control, and a multi-tenant server with an authoring surface. Every other project covers one or two of those.

## What the comparison says about widgentic

**Distinct, defensible today.**

- The only path that puts a *designed* widget inline in ChatGPT, claude.ai and VS Code without the host learning anything new. A2UI needs a renderer in the host; AG-UI needs to own the application; raw MCP Apps needs the server to write HTML per tool.
- Tables and trees as first-class kinds. A2UI's basic catalog has neither.
- Server-side actions with secrets, scopes and redaction; a written trust model; validation on write and read. No other project in the table ships a tenancy story.
- The agent-facing side of a result: descriptors as steering, structured errors, hint and action notes, model-context slimming, an authoring guide derived from the validators.
- Token economy: a kind and its data, not a layout and its data, on every turn.

**Behind, and the field has shown the shape of the fix.**

- No input from the reader. A2UI's two-way-bound inputs with closed-vocabulary validators and AG-UI's interrupt `responseSchema` are the two designs to borrow from.
- No Markdown, no media beyond `img`, no tabs or modal. A2UI's `Text` is Markdown.
- Web DOM only. A2UI renders natively on Flutter today and on Compose and SwiftUI soon.
- No presence in owned applications built on AG-UI/CopilotKit, which is where the agent frameworks (LangGraph, CrewAI, ADK, Strands, Microsoft Agent Framework, Pydantic AI, Mastra, Agno, the Claude Agent SDK) send their UI.
- Ecosystem gravity: A2UI has Google, 16k stars and a certification program on the roadmap; AG-UI has every framework and $27M behind it.

**Convergent decisions that validate the invariants.** A2UI removed agent theming in v1.0 for lack of uptake; widgentic never allowed it. AG-UI's draft spec says model output is untrusted and must never be rendered as executable markup; widgentic's tree is built with `createElement` behind allowlists. Both A2UI and widgentic return structured validation errors for the model to correct. The "templates are data" invariant is now the industry position, not an outlier.

## Recommended next steps, by value

1. **Probe, then adapt, into AG-UI applications.** Zero-code first: point CopilotKit's `@ag-ui/mcp-apps-middleware` at a widgentic server and see whether the `ui://widgentic/app.html` template mounts, whether `ui/message` and `serverTools` work there. Then a thin renderer that mounts the `application/vnd.widgentic+json` block with `mountWidget` from `@widgentic/core`. This is the cheapest way into every agent framework at once, because AG-UI already carries MCP tool results and `@widgentic/core` is browser-safe with zero dependencies. Detail: [widgentic and AG-UI](/compare/ag-ui).
2. **Publish a widgentic A2UI catalog and a `toA2UI` projection.** A custom catalog is a JSON Schema document; the render tree is pure data. `WgCard`, `WgTable`, `WgTree`, `WgGroup` as A2UI components give A2UI the table and tree it lacks and give widgentic every A2UI renderer (React, Lit, Angular, Flutter, Lynx) and transport (A2A, AG-UI). Detail: [widgentic and A2UI](/compare/a2ui).
3. **Design bounded input for actions** on the A2UI + AG-UI shape: two-way binding into a widget-local model, a closed validator set, `action.input` reading from the model, and a typed answer. This closes the largest functional gap and is already a backlog item.
4. **Adopt RFC 6902 for the `patch` output mode**, so an action result is forwardable as an AG-UI `STATE_DELTA` or an A2UI `updateDataModel`, and the authoring contract loses a bespoke grammar. Keep `merge` and `replace` as defaults.
5. **Stable node ids in `structuredContent.tree`** for template kinds: enables streaming preview of custom kinds and replaces the positional diff on the backlog with a keyed one.
6. **Markdown as a bind mode** rendered through the tree, never `innerHTML`.
7. **A public conformance fixture set** for the payload contract (payload in, tree out), the prerequisite for anyone else's renderer and for the A2UI catalog to prove equivalence.
8. **Position by complement**, in the sentence form AG-UI made familiar: *MCP gives agents tools; AG-UI brings agents into your application; A2UI lets an agent compose a screen; widgentic gives tool results a designed face any MCP host can show.* Publishing these pages is a `[USER]` call: they are analysis, and they name other projects.
