`@widgentic/mcp/sdk` exports one function, `createWidgenticServer(options?)`, returning a connectable `McpServer` from the official MCP TypeScript SDK 2.x (`@modelcontextprotocol/server`) with the full wiring: the nine tools, the MCP Apps declaration, the app template resource, output slimming and image inlining. The SDK packages are optional peers of `@widgentic/mcp`, so install them alongside, with `zod`, which ext-apps needs as its own peer:

```bash
npm install @widgentic/mcp @modelcontextprotocol/server @modelcontextprotocol/ext-apps zod
```

The smallest server serves exactly the built-in kinds and themes over stdio, to clients on protocol revision 2026-07-28 and on the 2025-era revisions alike:

```ts
import { createWidgenticServer } from "@widgentic/mcp/sdk";
import { serveStdio } from "@modelcontextprotocol/server/stdio";

serveStdio(() => createWidgenticServer());
```

A server in another language embeds the runtime-neutral `@widgentic/mcp/host` bundle instead of porting the engine; for .NET, that is the `Widgentic.Mcp` package ([Packages](/develop/packages)).

## The stdio example

The repository's `examples/mcp-server/main.ts` is the template for a deployment with your own widgets compiled in. Run it from a checkout with `npm run mcp`, or register it with a host:

```bash
claude mcp add widgentic -- npx tsx /path/to/widgentic/examples/mcp-server/main.ts
```

Author widgets in the designer, export them as TypeScript (the export matches the example's `widgets/` module shape), register them into a catalog and hand it to the assembly. Compiled-in widgets bind their actions inline, so the action source walks the same definitions:

```ts
import { serveStdio } from "@modelcontextprotocol/server/stdio";
import { createWidgenticServer } from "@widgentic/mcp/sdk";
import { createCatalog, findActionBinding, registerTemplate } from "@widgentic/core";
import { customWidgets } from "./widgets/index.js";

const catalog = createCatalog();
for (const widget of customWidgets) {
  registerTemplate(catalog, widget.kind, widget.template, widget.descriptor);
}

const byKind = new Map(customWidgets.map((widget) => [widget.kind, widget]));
serveStdio(() => createWidgenticServer({
  catalog,
  actions: {
    bindingAt: (kind, id) => {
      const widget = byKind.get(kind);
      return widget === undefined ? undefined : findActionBinding(widget.template, id);
    },
    load: (kind) => byKind.get(kind)?.load,
    resolve: () => undefined
  },
  scopes: ["read", "execute"]
}));
```

A stdio server runs on the operator's own machine, which is why the example grants `execute`.

## Options

With no options the assembly serves the built-ins; everything else is your explicit choice.

| Option | What it does |
|---|---|
| `catalog` | the composed `WidgetCatalog` to serve; omitted, exactly the built-in kinds |
| `themes` | the composed `ThemeRegistry`; omitted, the built-in themes |
| `schemas` | an async source of shared schemas, read only when `list_schemas` is called; omitted, empty |
| `sharedActions` | an async source of the STORED shared actions, read only when `list_actions` is called — the handler reduces each entry to its contract, so the URL, headers and query never leave the server; omitted, empty |
| `resourceDomains` | domains the app frame may load assets from directly: your own list, followed by the caller's `resourceDomains` setting (`composeResourceDomains`). Entries such as `cdn.example.com` or `*.example.com` are read by the core rule, refused ones dropped, and the rest declared as canonical `https://` origins in `_meta.ui.csp.resourceDomains`. Images on them are inlined only with the room undeclared images leave, and one left external keeps its URL for hosts that honor the declaration. Stored widgets and render inputs can never extend it |
| `resources` | the caller's stylesheets (`composeResources`), linked by every frame and `page` document their renders produce and listed by `list_themes`; an entry the core rule refuses, or whose host `resourceDomains` does not cover, is dropped. Omitted, nothing is linked |
| `actions` | the action source for the catalog: `bindingAt(kind, id)`, `load(kind)`, `resolve(ref)`; omitted, `execute_action` answers `UNKNOWN_ACTION` |
| `scopes` | the caller's scopes; `execute` gates `execute_action` and http-bound descriptors |
| `secrets` | `(name) => Promise<string>` resolving the caller's secret at execution time, `undefined` for an unknown name |
| `rateLimit` | a `() => boolean` gate for `execute_action`; `false` answers `RATE_LIMITED`; omitted, executions are not limited |
| `previewRateLimit` | a `() => boolean` gate for `preview_widget`; `false` answers `RATE_LIMITED`; omitted, previews are not limited |
| `fetchDeps` | an injectable transport for tests |

Catalog and themes are passed in because the trust decision belongs where the API key is read.

## Transports and environment

The assembly is transport-agnostic. Serve it through the SDK's entries, which speak protocol revision 2026-07-28 and the 2025-era revisions from the same factory: `serveStdio(factory)` over stdio, and `createMcpHandler(factory)` over Streamable HTTP. A server connected to a transport directly (in-memory pipes in tests, for example) speaks the 2025 era only.

Over HTTP the handler calls the factory once per request with the inbound `Request`. Resolve the caller's principal from the presented API key there, and build that request's server. Composition caches nothing, so one principal's widgets never reach another's session. A key that resolves to no principal degrades to the anonymous catalog, never to an error, and is never logged. On Node, wrap the handler with `toNodeHandler` from `@modelcontextprotocol/node`:

```ts
import { createServer } from "node:http";
import { createMcpHandler } from "@modelcontextprotocol/server";
import { toNodeHandler } from "@modelcontextprotocol/node";

// serverFor: see "Give it a store" below.
const handler = createMcpHandler(({ requestInfo }) =>
  serverFor(requestInfo?.headers.get("x-api-key") ?? undefined)
);
createServer(toNodeHandler(handler)).listen(8081, "127.0.0.1");
```

The handler verifies no token and validates no `Host` or `Origin` header. Put your own checks, CORS and body limit in front of it, as the [self-hosting example](/develop/self-hosting) does. Browser hosts on 2026-07-28 send `Mcp-Method` and `Mcp-Name` headers, so allow them in CORS.

Two environment variables are read each time a server is constructed:

- `WIDGENTIC_ASSUME_UI` — `1` or `true` slims the default-format `render_widget` result (a one-line confirmation instead of the full HTML text block) for calls that reveal no client capabilities. The client's own capabilities always decide first, in either direction: those a 2025-era session negotiated at `initialize`, or those a 2026-07-28 request carries in its `_meta`. The fallback matters for stateless 2025-era HTTP, where each request builds a server that never saw `initialize`. Explicit `format` values are never slimmed.
- `WIDGENTIC_INLINE_IMAGES` — `0` or `false` disables server-side image inlining. By default the iframe-facing surfaces of a result (`structuredContent.html`, `structuredContent.tree` and the `ui://widgentic/page/<kind>` resource) get `https` image sources rewritten to `data:` URIs through the guarded fetch, because Apps-host sandboxes block external images.

## Give it a store

`@widgentic/mcp/store` turns an API key into a principal. `createMemoryStore(seed?, limits?, options?)` serves tests and demos; `createFileStore(dir, options?)` reads this layout:

```text
<dir>/principals.json                     [{ id, scopes, keyDigest }]  # sha256 digests, never raw keys
<dir>/<principalId>/widgets/<kind>.json   { kind, template, descriptor }
<dir>/<principalId>/themes/<name>.json    { name, label?, tokens, styles? }
<dir>/<principalId>/schemas/<name>.json   { name, label?, description?, schema }
<dir>/<principalId>/actions/<name>.json   { name, label?, description?, definition }
<dir>/<principalId>/secrets/<name>.json   envelope records, ciphertext only
<dir>/<principalId>/settings.json         { defaultThemes?: { light?, dark? }, resourceDomains?: string[], resources?: { type, href, integrity? }[] }
```

`settings(principalId)` and, on writable stores, `putSettings(principalId, update)` hold one settings record per principal: a write replaces the sections it names (`null` removes one) and keeps the rest. Its `defaultThemes` section names the stored theme light and dark hosts get when a render names no theme; `composeThemes` turns it into the registry's defaults, and a theme named there cannot be removed (`THEME_IN_USE`); a default naming no stored theme is refused with `UNKNOWN_THEME`. Its `resourceDomains` section lists up to 20 domains the caller's frames may load images from directly, stored as canonical origins; an entry the rule refuses is `INVALID_DOMAIN`, and `composeResourceDomains` yields the list for `createWidgenticServer`. A record or section of the wrong shape (an unknown section or mode, more than 20 domains) is `INVALID_SHAPE`, and a refused write changes nothing. Its `resources` section lists up to 8 stylesheets every frame links, `{ type: "stylesheet", href, integrity? }`: an `https://` address whose host the same record's `resourceDomains` must cover, so a stylesheet on an undeclared host, or a write that removes a domain a stylesheet needs, is refused with `UNDECLARED_DOMAIN`, and a malformed entry or another type with `INVALID_RESOURCE`. `composeResources` yields the list for `createWidgenticServer`. Read the record once per request with `readPrincipalSettings` and pass it to each composition as `{ settings }`.

Options carry `limits` (how many widgets, themes, schemas, actions and secrets a principal may hold, the bytes per entry and the template nodes per widget — the defaults are on [Limits](/reference/limits)), an `onDiagnostic` sink and a `cipher` for secrets. Per request:

```ts
import {
  ANONYMOUS_PRINCIPAL,
  composeCatalog,
  composeResourceDomains,
  composeResources,
  composeThemes,
  createFileStore,
  readPrincipalSettings
} from "@widgentic/mcp/store";
import { createWidgenticServer } from "@widgentic/mcp/sdk";
import {
  createExecutionLimiter,
  DEFAULT_EXECUTIONS_PER_MINUTE,
  DEFAULT_PREVIEWS_PER_MINUTE
} from "@widgentic/mcp";

const store = createFileStore("./data");
// Built once: the buckets must outlive the per-request servers.
const executions = createExecutionLimiter(DEFAULT_EXECUTIONS_PER_MINUTE);
const previews = createExecutionLimiter(DEFAULT_PREVIEWS_PER_MINUTE);

async function serverFor(apiKey: string | undefined) {
  const resolved = apiKey === undefined ? undefined : await store.resolvePrincipal(apiKey);
  const { id, scopes } = resolved ?? ANONYMOUS_PRINCIPAL;
  const catalog = await composeCatalog(store, id, { executeAllowed: scopes.includes("execute") });
  const settings = readPrincipalSettings(store, id);
  const themes = await composeThemes(store, id, { settings });
  const domains = await composeResourceDomains(store, id, { settings });
  const stylesheets = await composeResources(store, id, { settings });
  return createWidgenticServer({
    catalog: catalog.value,
    themes: themes.value,
    resourceDomains: domains.value,
    resources: stylesheets.value,
    actions: catalog.actions,
    scopes,
    schemas: () => store.schemas(id),
    sharedActions: () => store.actions(id),
    secrets: (name) => store.secretValue(id, name),
    rateLimit: () => executions.take(id),
    previewRateLimit: () => previews.take(id)
  });
}
```

`composeCatalog` and `composeThemes` return fresh instances every time, each with a `diagnostics` array: an invalid, oversized or built-in-shadowing entry is skipped with a diagnostic, never fatal. `createExecutionLimiter(perMinute)` keeps one token bucket per principal id: build it once, outside the factory — a limiter built per request starts full every time and limits nothing — and keep executions and previews in separate buckets, so a burst of streaming previews never spends a principal's actions. Keys are stored as `sha256:` digests and compared in constant time (`generateKey`, `hashKey`, `verifyKey`); a key carries `read` and optionally `execute`, fixed at creation.

### SQLite

`@widgentic/mcp/store/sqlite` exports `createSqliteStore(path, options?)`, a `WritableWidgetStore` over a single database file using the Node runtime's built-in SQLite — no dependency, not even an optional peer. It opens the file in WAL mode so a read-only MCP process and a writing authoring app can share it, runs every write in one transaction (a refusal leaves nothing behind), and stores key digests and secret ciphertext only. Options carry `limits`, `onDiagnostic` and a `cipher`, like the other implementations, and the returned store adds `close()`. It is a single-node design: reads and writes are synchronous statements, bounded by the store limits — past that ceiling you want a server database, not this adapter. The [self-hosting example](/develop/self-hosting) runs on it.

### Cosmos DB

`@widgentic/mcp/store/cosmos` exports `createCosmosStore(options)`, a `WritableWidgetStore` over two containers: `data`, partitioned by `/principalId` with one document per entry (`profile`, `widget:<kind>`, `theme:<name>`, `schema:<name>`, `action:<name>`, `secret:<name>`) plus a `settings` document holding the principal's settings record, so a principal's catalog is one single-partition query; and `keys`, partitioned by `/digest`, so key resolution is a point read. It takes an `endpoint` and an Azure `credential` (managed identity in deployment) plus optional `databaseId`, `dataContainerId`, `keysContainerId`, `limits`, `cipher` and `log` — deliberately no account-key or connection-string option. Under Cosmos RBAC the serving identity can hold the read-only role, so a write from the MCP server fails at the service. `@azure/cosmos` and `@azure/identity` are optional peers of this entry.

## Mount the authoring surface

The write side — how people author the entries the store serves — ships as `@widgentic/mcp/authoring`. `handleAuthoringRequest({ method, path, body, context }, deps)` is a pure core over the writable store: widgets, themes, schemas and shared actions (the path names the entry; the body can never redirect it), the principal's settings at `/settings`, the action test call through the guarded fetch, write-only secrets, and API keys minted once with fixed scopes. `createAuthoringHttpHandler(deps, resolveContext)` mounts it on `node:http` under `/api`.

`GET /preview-frame` serves the designers' preview frame (see [Embed the designers](/develop/embed-the-designers#the-preview)). It answers with the app template as HTML, under a Content-Security-Policy built from your operator domains (`deps.resourceDomains`, the list your MCP server declares for everyone) followed by the signed-in principal's `resourceDomains` setting. That is the list `createWidgenticServer` declares for that principal, so the preview loads what a host would. Its scripts are allowed only by hash. It may be framed only by its own origin, connects nowhere (`connect-src 'none'`), loads images, styles, fonts and media only from the declared domains, and is never cached. Without a principal, or when the settings read fails, the policy carries the operator domains alone.

Authentication is yours: the surface begins where it ends. Your `resolveContext(req)` returns `{ principalId, subject?, label? }` however you authenticate — a session cookie, a trusted proxy header, or a fixed principal for a single-user deployment — and identity routes (linked accounts) exist only when you supply a `subject`. Two rules are the surface's own and cannot be dropped by a host: a presented widgentic API key is refused with `401 KEY_NOT_A_SESSION` before any store access (keys travel into prompt-injectable hosts and must never author), and nothing in a request can name a principal other than the one you resolved.

```ts
import { createAuthoringHttpHandler } from "@widgentic/mcp/authoring";

const handle = createAuthoringHttpHandler({ store, secretsEnabled: true, limiter }, async (req) => {
  const session = readMySession(req);
  if (session === undefined) return undefined; // → 401 NO_PRINCIPAL
  const principal = await store.ensurePrincipal(session.subject, session.label);
  return { principalId: principal.id, subject: session.subject, label: session.label };
});
```

## Secrets

Http actions reference secrets by name; `@widgentic/mcp/secrets` stores them as envelope-encrypted records. `encryptSecret(value, cipher)` generates a fresh 256-bit data key, encrypts the value with AES-256-GCM, wraps the data key through the cipher port and returns `{ alg, kekVersion, wrappedKey, iv, ciphertext, tag }`; `decryptSecret` reverses it and `rewrapSecret` moves a record to a newer key version without decrypting the value. Values are 8 to 4096 bytes.

A `SecretCipher` only wraps and unwraps data keys. `createLocalCipher(hexKey)` keeps a 64-hex-character key in memory (`generateLocalKek()` makes one) — the cipher for development rigs and for [self-hosted single-node deployments](/develop/self-hosting), where the operator supplies the key from a mounted file or an environment variable and protects it like the credentials it encrypts: whoever can read that material can decrypt that deployment's records. Vault-backed custody stays the stronger arrangement and is what widgentic's own deployment uses. `@widgentic/mcp/secrets/keyvault` exports `createKeyVaultCipher({ keyId, credential, previous? })`, which wraps and unwraps through the vault's cryptographic operations so the key-encryption key never enters the process; the identity needs only the wrap/unwrap role on that key, and `previous` maps older key versions to clients until records are re-wrapped. Hand the cipher to the store's `cipher` option; without one the store refuses `putSecret` and `secretValue` with `NO_CIPHER`. Secrets are injected only at execution, never displayed, and redacted from every message the server emits.
