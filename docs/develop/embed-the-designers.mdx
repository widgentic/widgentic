---
title: "Embed the designers"
description: "Mount the widget, theme, schema, action and settings designers in your own page as functions or custom elements, and theme their chrome."
---

`@widgentic/designer` ships five designers — widget, theme, schema, action and settings — each as a function taking a container and each as an opt-in custom element. They run in the browser, depend only on `@widgentic/core`, and perform no network I/O of their own: every edit re-runs widgentic's validators and re-renders a live preview through the real pipeline; persistence is yours. The one load they cause is the preview frame you name with `previewFrame`, which the browser fetches from your server.

```bash
npm install @widgentic/designer
```

## The widget designer

```ts
import { createDesigner } from "@widgentic/designer";

const designer = createDesigner(document.querySelector("#host")!, { themes: [] });
designer.subscribe((draft) => save(draft));
```

`createDesigner(container, options?)` accepts:

| Option | Purpose |
|---|---|
| `initialWidget` | a widget definition to open with (otherwise a starter draft) |
| `initialTheme` | a token map for the preview |
| `themes` | named theme entries offered as preview themes; theme authoring lives in the theme designer |
| `previewTheme` | the person's own pick among `themes` to open with as the preview theme, its tokens and shared styles applied — pass it to keep a pick across a remount; an unknown name is ignored |
| `defaultPreviewTheme` | the host's fallback preview theme, one name or `{ light?, dark? }` such as the person's Settings defaults; used when there is no `previewTheme` and the widget's `descriptor.themes` names no supplied theme for the designer's scheme |
| `schemas` | shared data-schema entries the draft may reference by name (`descriptor.dataSchemaRef`) |
| `actions` | shared actions the draft may bind by name, for element bindings and the widget-level `load` |
| `secretNames` | secret names offered when an inline http action needs a header or query secret |
| `appearance` | `"auto"` (default, follows `prefers-color-scheme`), `"light"` or `"dark"` for the designer's own chrome |
| `chrome` | host chrome tokens, see below |
| `readOnly` | mount with every editing surface inert |
| `resources` | the person's stylesheets, as their settings record holds them; the preview frame links the entries `parseResource` accepts, and the in-page preview ignores them |
| `previewFrame` | the URL of a preview frame, such as the authoring surface's `/api/preview-frame`: the preview then runs in that frame instead of the page (see [The preview](#the-preview)) |

The handle is `{ getDraft, getDiagnostics, loadWidget, checkWidget, loadTheme, setReadOnly, subscribe, dispose }`. `getDraft()` returns a copy of the current draft; `getDiagnostics()` returns its diagnostics and `checkWidget(definition)` checks a definition as a load would, without touching the draft, both resolved against the `schemas` and `actions` you supplied; `loadWidget(definition)` and `loadTheme(theme)` validate first and return `{ ok: true }` or `{ ok: false, errors }` without touching the draft on failure; `loadTheme(tokens)` layers its tokens over the preview theme the person chose, which stays selected with its styles, so `loadTheme({})` returns to it; `loadWidget` keeps the preview theme and refuses a kind Save would refuse only when the load changes the kind; `subscribe(listener)` calls `listener(draft, diagnostics)` on every change and returns an unsubscribe function; `dispose()` removes the UI. Read-only mode — `readOnly: true` or `setReadOnly(true)` — leaves editing surfaces visible but inert while the preview, its theme selector and Export keep working: it restricts editing, not looking.

## Theme, schema, action and settings designers

```ts
import {
  createActionDesigner,
  createSchemaDesigner,
  createSettingsDesigner,
  createThemeDesigner
} from "@widgentic/designer";

const themeDesigner = createThemeDesigner(el, { widgets, readOnly });
// → { getTheme, loadTheme, setReadOnly, subscribe, dispose }

const schemaDesigner = createSchemaDesigner(el, { readOnly });
// → { getSchema, loadSchema, setReadOnly, subscribe, dispose }

const actionDesigner = createActionDesigner(el, { schemas, secretNames, testCall });
// → { getAction, loadAction, setReadOnly, subscribe, dispose }

const settingsDesigner = createSettingsDesigner(el, { themes, initialSettings, readOnly });
// → { getSettings, loadSettings, setThemes, setReadOnly, subscribe, dispose }
```

- `createThemeDesigner` edits a named entry `{ name, label?, description?, tokens, styles? }`, its shared styles in the widget designer's own Styles panel. Its `widgets` option adds custom widget definitions to the preview-kind selector beside the built-ins, so a theme is judged against the widgets it will dress; invalid definitions are skipped. `initialTheme` opens an existing entry. It takes `previewFrame` and `resources` too.
- `createSchemaDesigner` edits a shared schema entry `{ name, label?, description?, schema }`; `initialSchema` opens one.
- `createActionDesigner` edits a stored action `{ name, label?, description?, definition }`; `initialAction` opens one. `schemas` offers shared schemas as copy-from sources for the input and output schemas, and `secretNames` offers names for header and query values. A Test control appears only when you pass `testCall(definition, args)`, which must run through your server's execution path — the library performs no network I/O itself.

- `createSettingsDesigner` edits the principal's settings record. Its **Default themes** subsection offers, per mode (light hosts, dark hosts), the built-in and every entry you pass in `themes`; `getSettings()` returns `{ defaultThemes: { light?, dark? } }`, built-in choices omitted, with any section it does not edit passed through untouched. Save it with `PUT /settings` on the authoring surface. A name you did not pass in `themes` shows as unavailable rather than disappearing. `setThemes(themes)` replaces the themes offered and keeps the record as it is. Its **Resource domains** subsection lists the domains the principal's frames may load images from directly. Each entry is checked as it is typed by the same rule the store applies (`parseResourceDomain` from `@widgentic/core`). A valid entry is recorded in its canonical `https://` form; an invalid one is kept as typed and marked, so the save's `INVALID_DOMAIN` names it. Adding stops at `RESOURCE_DOMAIN_LIMIT`. `getSettings()` carries `resourceDomains` once the record had it or the person edited the list, so a save clears an emptied list. Its **Stylesheets** subsection lists `{ type: "stylesheet", href, integrity? }` entries the same way, checked by `parseResource` against `RESOURCE_LIMIT`. An entry whose host none of the listed domains covers (`resourceCovered`) is marked with the domain to add, and the mark clears as soon as that domain is listed. `getSettings()` carries `resources` on the same terms as `resourceDomains`.

## The preview

The widget and theme designers preview in one of two ways.

**In a frame (`previewFrame`).** The preview runs in the document MCP Apps hosts mount: the app template, framed with `sandbox="allow-scripts"`, and the designer acts as its host. The frame's bridge mounts and patches each render as it does in Claude or ChatGPT, under the image, style, font and media policy hosts apply for the person's resource domains. So an image from a declared domain loads, and an undeclared one is blocked, exactly as in a conversation. Neither your page's styles nor the preview's cross the frame.
- **The route.** Serve the frame with the authoring surface's `GET /preview-frame` (see [Run your own server](/develop/run-your-own-server#mount-the-authoring-surface)). It needs no sign-in, and grants a signed-in person their own domains; a widgentic API key is refused there as on every authoring route.
- **The frame never executes.** It has no server tools: actions show as unavailable, and nothing leaves the designer. Links open in a new tab when they are `http`, `https`, `mailto` or `tel`.
- **The color scheme.** The frame follows the designer's: `appearance` when you pin it, otherwise your page's `data-theme` on `<html>`, otherwise `prefers-color-scheme`. Under "none", the preview wears widgentic's built-in light or dark palette. A preview theme the person picks applies to both, as an explicit `theme` does in a render.
- **Stylesheets.** Pass the person's `resources` too, and the frame links them as hosts do ([Stylesheets](/how-it-works/inline-rendering#stylesheets)). The in-page preview never adds a stylesheet to your page.
- **The custom elements** take it as the `preview-frame` attribute.

<Note>`previewFrame` and `GET /preview-frame` are available from `@widgentic/designer` and `@widgentic/mcp` 0.14.0.</Note>

**In the page (the default).** Without `previewFrame`, the preview renders in your page's DOM, with no server needed. Its styles stay inside it: the widget's and the theme's rules are scoped to the preview. Your page's element rules are another matter. A rule like `header { border-bottom: … }` would dress a widget's `<header>` that no MCP Apps host dresses, so fence them out of the preview:

```css
header:where(:not(.wgd-preview *)) { border-bottom: 1px solid var(--line); }
button:where(:not(.wgd-preview *)) { padding: 4px 10px; }
```

`:where()` keeps the rule's weight unchanged. Rules on your own classes need no fence. In the page, your page's own policy decides what a preview may load, not the person's resource domains.

All five accept `appearance`, `chrome` and `readOnly`. The widget designer only selects among the themes, schemas and actions you pass; authoring each belongs to its own designer, so a host ships only what it embeds.

## Custom elements

Registration happens only through the explicit calls — importing the module has no registry side effects:

```ts
import {
  defineDesignerElement,
  defineThemeDesignerElement,
  defineSchemaDesignerElement,
  defineActionDesignerElement,
  defineSettingsDesignerElement
} from "@widgentic/designer";

defineDesignerElement();          // <widgentic-designer>
defineThemeDesignerElement();     // <widgentic-theme-designer>
defineSchemaDesignerElement();    // <widgentic-schema-designer>
defineActionDesignerElement();    // <widgentic-action-designer>
defineSettingsDesignerElement();  // <widgentic-settings-designer>
```

Each registrar takes an optional tag name and does nothing if that tag is already defined. The elements wrap their factory and re-emit its subscription as bubbling `widgentic-change` CustomEvents whose `detail` carries `{ draft, diagnostics }`, `{ theme }`, `{ schema }`, `{ action }` or `{ settings }`. Two attributes are read when the element connects: `appearance` (`light` or `dark`) and `chrome` (the token map as JSON). `<widgentic-designer>` and `<widgentic-theme-designer>` also read `preview-frame`. The wrapped handle is available as the element's `designer` property. `<widgentic-settings-designer>` also takes its choices through a `themes` property (`{ name, label? }` entries), settable before or after the element connects, or before it is defined; a change after connecting reaches the mounted designer through `setThemes`.

Without a bundler, load the single-file bundle and use the elements directly:

```html
<script type="module" src="/node_modules/@widgentic/designer/dist/browser/widgentic-designer.js"></script>
<widgentic-designer></widgentic-designer>
```

## Theming the chrome

<Note>`chrome` is available from `@widgentic/designer` 0.2.0. From 0.3.0 the built-in defaults are the widgentic palette, and `CHROME_DEFAULTS` and `chromeCss` are exported.</Note>

The designers paint their own UI — panels, inputs, buttons, tags, menus — through 28 `--wgd-*` custom properties, the chrome tokens (exported as `CHROME_TOKENS`). The widget preview inside them is not chrome: it follows the selected theme's `--wg-*` tokens from `@widgentic/core/theming` and is unaffected by `chrome`.

By default the designers wear the **widgentic palette**, light and dark — the same colours the product uses, so an embedded designer looks like widgentic without you configuring anything. Every colour sits on the logo mark's hue, and each one is contrast-checked in both schemes: text pairs at WCAG AA (4.5:1), and the borders that identify an input, a focused tag or a banner at 3:1. Typography is deliberately *not* branded — `font`, `font-mono` and the three sizes stay system values, because a library must never default to a webfont it cannot serve.

`appearance` picks which scheme's defaults the chrome follows. `chrome` layers your values on top of them, applied inline on the designer root, so they win over the light and dark blocks:

```ts
import { createDesigner } from "@widgentic/designer";

createDesigner(host, {
  chrome: {
    bg: "var(--app-bg)",            // var() references follow the host's own scheme switching
    panel: "var(--app-panel)",
    accent: "#40a0c8",
    font: "var(--app-font, system-ui, sans-serif)",
    radius: "8px"
  }
});
```

The elements take the same map as JSON:

```html
<widgentic-designer chrome='{"accent":"#40a0c8","font-size":"14px"}'></widgentic-designer>
```

| Group | Tokens | Default |
|--|--|--|
| Surfaces | `bg`, `panel`, `hover` | light/dark palette |
| Lines | `border`, `line` | light/dark palette |
| Text | `text`, `muted` | light/dark palette |
| Accent | `accent`, `accent-bg`, `accent-line` | light/dark palette |
| Danger | `danger`, `danger-bg`, `danger-line` | light/dark palette |
| JSON highlight | `hl-key`, `hl-str`, `hl-num`, `hl-bool`, `hl-punct` | light/dark palette |
| Typeface | `font` (labels, buttons, controls), `font-mono` (code panes, code-like values) | `system-ui, sans-serif` / `ui-monospace, monospace` |
| Size | `font-size` (base), `font-size-sm` (compact rows), `font-size-xs` (badges, tags, meta) | `13px` / `12px` / `11px` |
| Shape | `radius-sm`, `radius`, `radius-lg`, `gap` | `4px` / `6px` / `8px` / `16px` |
| Elevation | `shadow` (menus) | `0 8px 24px -12px rgba(11, 27, 38, 0.35)` |

### Match your page to the designers

`CHROME_DEFAULTS` is not a description of the defaults — it *is* them; the injected stylesheet is generated from it. Paint your own surfaces from the same object and the two can never drift — and `chromeReferences()` is the return trip: the full `chrome` map of `var()` references under the same prefix, so the designers follow whatever your page declares. Together they are the full-takeover recipe:

```ts
import { CHROME_DEFAULTS, chromeCss, chromeReferences, createDesigner } from "@widgentic/designer";

// Your page declares the palette — light, system dark, and an explicit
// toggle block your own theme switcher drives with one root attribute.
const style = document.createElement("style");
style.textContent = chromeCss(CHROME_DEFAULTS, {
  prefix: "--host",
  selector: ":root",
  darkMediaSelector: ':root:not([data-theme="light"])',
  darkSelector: ':root[data-theme="dark"]'
});
document.head.append(style);

// The designers reference those properties inline, so a scheme change
// repaints MOUNTED designers through the cascade — no remount, no event,
// and unsaved drafts survive. Spread-override what you want to differ.
createDesigner(host, { chrome: { ...chromeReferences(), font: "Inter, sans-serif" } });
```

<Warning>A `var()` reference to a property your page never defines is **invalid at computed-value time** — it does not fall back to the built-in defaults. Pair `chromeReferences()` with `chromeCss` under the same prefix, and use a partial `chrome` map instead when you only want to change a few tokens (unmapped tokens keep the product defaults).</Warning>

Painting the page directly from the exported object also works:

```ts
import { CHROME_DEFAULTS, chromeCss } from "@widgentic/designer";

const style = document.createElement("style");
style.textContent = chromeCss(CHROME_DEFAULTS, { prefix: "--app" });
document.head.appendChild(style);
// Your page now has --app-bg, --app-panel, --app-accent … in both schemes.
```

`chromeCss(palette, options?)` takes `prefix` (default `--wgd`), `selector` (default `:root`), `darkMediaSelector` and an optional `darkSelector` for a toggle you control. It returns a string; nothing is injected for you.

### Use your own palette instead

There is one default palette and no second one to fall back to — a host that wants a different look passes its own values, and `chromeCss` will render them for the surrounding page just the same:

```ts
import { chromeCss, createDesigner } from "@widgentic/designer";
import type { ChromePalette } from "@widgentic/designer";

const mine: ChromePalette = { light: { /* every token */ }, dark: { /* every token */ } };

createDesigner(container, { chrome: mine.light });
document.head.appendChild(
  Object.assign(document.createElement("style"), { textContent: chromeCss(mine, { prefix: "--app" }) })
);
```

Contrast is then yours to own: the thresholds the built-in palette is held to are in `chrome-contrast.test.ts` if you want the same gate.

Rules: values are CSS values; CSS-wide keywords (`inherit`, `initial`, `unset`, `revert`) are ignored — on a custom property they act on the token itself, not on what reads it — so to follow your typeface pass its variable with a fallback stack (`font: "var(--app-font, system-ui, sans-serif)"`). Unknown tokens, non-string values and unparseable attribute JSON are ignored, never thrown. With no `chrome`, you get the widgentic palette.

## Helpers
