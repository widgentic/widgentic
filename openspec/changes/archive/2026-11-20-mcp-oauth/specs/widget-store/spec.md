## ADDED Requirements

### Requirement: Access grants bind a host to a key
The `./store` entry SHALL export an access-grant port beside the widget store, implemented by every adapter: a read side that resolves an access token, and a write side — on the writable adapters only — that stores and consumes authorization codes, creates a grant from a consumed code, rotates a grant's tokens, revokes a grant and lists a principal's grants. A grant SHALL record its principal, the API key it is bound to, the client's id and name, the resource it was issued for, its scopes and its timestamps. Access tokens, refresh tokens and authorization codes SHALL be generated by the store with distinct greppable prefixes, returned raw exactly once, and held only as `sha256:<hex>` digests compared in constant time; none SHALL reach a log line. A principal SHALL hold at most the configured number of grants (`StoreLimits`, default 50); creating one beyond it SHALL end the principal's least recently used grant rather than refuse. The read-only file store SHALL carry no write side and SHALL resolve only the anonymous form.

#### Scenario: A token resolves to the key's principal and scopes
- **WHEN** a grant is created for principal `P` through key `ops` (`read`, `execute`) for resource `R`, and its access token is resolved for `R`
- **THEN** the result SHALL be `P` with scopes `read` and `execute` and no identity `subject`

#### Scenario: Stored material is hashed
- **WHEN** a grant is created and the store's serialized state is inspected
- **THEN** neither the access token, the refresh token nor the authorization code SHALL appear in it; only their digests SHALL

#### Scenario: The grant limit retires the oldest connection
- **WHEN** a principal at the grant limit receives one more grant
- **THEN** the new grant's token SHALL resolve, and the token of the grant used least recently SHALL no longer resolve

#### Scenario: The adapters agree
- **WHEN** the shared port contract suite runs against the memory, SQLite and Cosmos adapters
- **THEN** every grant scenario SHALL pass identically on each

### Requirement: Token resolution is exact, bounded and read-only
Resolving an access token SHALL return `undefined` — never an error and never a partial match — for a token that is unknown, malformed, expired, issued for a different resource than the one asked for, superseded by a rotation, or belonging to a revoked grant or a revoked key. Resolution SHALL require no write and SHALL work through a read-only handle. In the Cosmos adapter it SHALL be a single-partition point read on the token's digest in the `keys` container, with no second read and no cross-partition query; expiry SHALL be decided from the record's own timestamp, never left to the container's time-to-live alone. A token of the anonymous form SHALL resolve to the anonymous principal with no store access at all. An API key presented as an access token, and an access token presented to `resolvePrincipal`, SHALL each resolve to nothing.

#### Scenario: Expired, foreign and unknown tokens resolve to nothing
- **WHEN** a token is resolved after its expiry, or for a resource other than its own, or was never issued
- **THEN** each result SHALL be `undefined`

#### Scenario: Token resolution is a point read
- **WHEN** an access token is resolved on the Cosmos adapter
- **THEN** exactly one read SHALL be made, of the `keys` container by the token's digest as both id and partition key
- **AND** a record whose expiry has passed but which the container has not yet removed SHALL resolve to `undefined`

#### Scenario: The anonymous token touches no store
- **WHEN** a token of the anonymous form is resolved
- **THEN** the result SHALL be the anonymous principal and no store read SHALL have occurred

#### Scenario: Keys and tokens are not interchangeable
- **WHEN** a valid API key is resolved as an access token, and a valid access token is passed to `resolvePrincipal`
- **THEN** both results SHALL be `undefined`

### Requirement: Codes are single-use and grants rotate
An authorization code SHALL be consumable once and only within sixty seconds of being stored; claiming it SHALL be atomic, so two exchanges never both succeed. A second attempt within the code's lifetime SHALL report the grant the first produced, so the caller can end it, and SHALL mark the code so that a first exchange still in flight ends its own grant; past its lifetime a code, used or not, SHALL be reported as unknown and SHALL end nothing. Rotating a grant SHALL issue a new access token (one hour) and a new refresh token (thirty days from this use) and SHALL make the previous access token unresolvable at once; a superseded refresh token SHALL be honored for sixty seconds after its rotation, and presenting it later — however many rotations ago it was superseded, until its own expiry — SHALL be reported as a replay. Rotation SHALL replace the grant conditionally, so of parallel rotations each caller receives a pair but only one pair is the grant's, and no token of the others SHALL remain resolvable. Rotation SHALL refuse, and end the grant, when the key it is bound to is no longer live. Revoking a grant SHALL make every token of it unresolvable. `revokeKey` SHALL revoke every grant bound to that key in the same operation — also when the key is already revoked, so repeating a revocation that failed part-way finishes it — and a principal's other keys and their grants SHALL be untouched.

#### Scenario: Two exchanges, one success
- **WHEN** the same code is consumed twice in sequence
- **THEN** exactly one call SHALL succeed, and the other SHALL report the code as used together with the grant the first produced
- **AND WHEN** the two arrive concurrently
- **THEN** at most one SHALL succeed, at least one SHALL report the code as used, and no token issued for that code SHALL resolve once the caller has ended the reported grant

#### Scenario: A late code is refused
- **WHEN** a code is consumed more than sixty seconds after it was stored
- **THEN** the call SHALL report it as unknown and no grant SHALL be created
- **AND WHEN** a code that was exchanged in time is presented again after those sixty seconds
- **THEN** the call SHALL report it as unknown and the grant it produced SHALL keep working

#### Scenario: Rotation supersedes the old pair
- **WHEN** a grant is rotated with its current refresh token
- **THEN** the new access token SHALL resolve and the previous one SHALL NOT
- **AND** the previous refresh token SHALL rotate again within sixty seconds and SHALL be reported as a replay after that

#### Scenario: An old refresh token is still a replay
- **WHEN** a grant has been rotated twice and its first refresh token is presented after the grace
- **THEN** the call SHALL report a replay and every token of the grant SHALL stop resolving

#### Scenario: Parallel rotations leave nothing behind
- **WHEN** one refresh token is rotated by three callers at once and the grant's key is then revoked
- **THEN** each caller SHALL have received a pair, exactly one access token SHALL have resolved before the revocation, and none SHALL resolve after it

#### Scenario: A stranded grant ends at its next refresh
- **WHEN** a key is revoked but one of its grants was not ended, and that grant's refresh token is presented
- **THEN** the call SHALL issue nothing and the grant's access token SHALL stop resolving

#### Scenario: A failed revocation is finished by repeating it
- **WHEN** `revokeKey` stamps the key and then fails before every grant is ended, and is called again
- **THEN** the second call SHALL end the remaining grants

#### Scenario: Revoking a key ends its grants only
- **WHEN** a principal holds grants through keys `laptop` and `ops`, and `ops` is revoked
- **THEN** the grants bound to `ops` SHALL stop resolving and rotating, and the grant bound to `laptop` SHALL keep working

### Requirement: Stores written before grants existed read unchanged
A store written by a version without access grants SHALL open and serve every principal, key, widget, theme, schema, action, secret and settings record exactly as before, with no migration step: the absence of any grant record SHALL mean "no grants". The SQLite adapter SHALL create what grants need on open without touching existing rows, and the Cosmos adapter SHALL require no new container.

#### Scenario: An old store opens and serves
- **WHEN** a store file or database written before this capability is opened
- **THEN** every key SHALL resolve as it did, every entry SHALL list as it did, and listing a principal's grants SHALL return an empty list

#### Scenario: Grants then work on the old store
- **WHEN** a grant is created on that store
- **THEN** its token SHALL resolve, and the pre-existing records SHALL be byte-identical to before
