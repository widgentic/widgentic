## Purpose

The public documentation site for widgentic at `docs.widgentic.dev`: what it is, how it works and how to use it, for people who design widgets and for developers who embed the packages or run a server — with the reference parts derived from the same validators the product enforces.

## ADDED Requirements

### Requirement: Documentation is a Mintlify site sourced from this repository
The documentation SHALL live in `docs/` at the repository root as a Mintlify project — a `docs.json` plus MDX pages — deployed from `main` and served at `https://docs.widgentic.dev`, with preview deployments for pull requests. `docs.json` SHALL carry the brand: the widgentic mark as logo (light and dark variants), the favicon, and theme colours drawn from the brand palette — link blue `#1E6F92` as the primary and button colour (widget blue `#40A0C8` does not reach the 3:1 contrast the accessibility gate requires on a light background) and widget blue `#40A0C8` as the dark-mode emphasis — and SHALL render in light and dark. The site SHALL mention no infrastructure facts (resource names, identities, regions); public endpoints (`widgentic.dev`, `mcp.widgentic.dev/mcp`) are allowed.

#### Scenario: The site builds from main
- **WHEN** a commit lands on `main` touching `docs/`
- **THEN** the site at `docs.widgentic.dev` SHALL reflect it, and a pull request touching `docs/` SHALL get a preview deployment

#### Scenario: The site wears the brand
- **WHEN** `docs.json` is inspected
- **THEN** it SHALL reference the mark for light and dark, the favicon, and the brand colours (`#1E6F92` primary/dark, `#40A0C8` light)

### Requirement: Information architecture serves designers and developers
The site SHALL be organised in five tabs — Get started, Design, How it works, Develop, Reference — and SHALL contain at least: **Get started:** what widgentic is, quickstart (sign in → design → key → connect → render), connect a host (claude.ai connector, Claude Desktop, VS Code Copilot Chat, Claude Code, the MCP basic-host, MCP Inspector), keys and scopes. **Design:** the widget designer, the template DSL and what templates cannot do, data schemas (inline and shared), themes and tokens, actions (prompt and http) and secrets, groups and hints, authoring with an agent (`get_authoring_guide` → import → validate → save). **How it works:** the payload contract, from payload to pixels, inline rendering in MCP Apps hosts and the text fallback, per-principal catalogs and keys, the trust model, the host support matrix. **Develop:** the three packages, render in your host, embed the designers, run your own server (stdio example, Streamable HTTP, store adapters, secrets), the MCP tools, API reference per package entry. **Reference:** the generated pages of the next requirement plus links to the package changelogs. Every page SHALL be reachable from `docs.json` navigation, and every internal link SHALL resolve.

#### Scenario: Both audiences find their path from the home page
- **WHEN** the home page is opened
- **THEN** it SHALL offer a designer path (Get started → Design) and a developer path (Develop) as its primary calls to action

#### Scenario: Navigation is complete
- **WHEN** the repository's docs navigation test and `mint broken-links --check-anchors` run
- **THEN** every MDX page under `docs/` SHALL appear in `docs.json` navigation (or carry `hidden: true` in its frontmatter), every navigation entry SHALL resolve to a page, and no internal link or anchor SHALL be broken

### Requirement: Reference pages are derived, never restated
The Reference tab's pages for the authoring contract (entry shapes, template DSL forms and safety rules, identifier rules, style and schema constraints, limits), the theme tokens (every token with type, use and default; the light defaults and the `dark` preset), the action definition (kinds, binding forms, scope semantics, the method/output-mode/name/length vocabulary), the seven MCP tools (name, description, input schema) and the export index of every published package entry SHALL be generated by `npm run docs:generate` from the exported constants and validators (`buildAuthoringGuide()` including its `actions` section, `TOKEN_SPECS`, `TOKEN_DEFAULTS`, `darkTheme`, `HTTP_METHODS`, `OUTPUT_MODES`, `PROMPT_TEXT_MAX`, `SECRET_NAME`, `ACTION_NAME`, the `*_TOOL` definitions, the entries' runtime exports) — not hand-written. The generated files SHALL be committed, carry a "generated — do not edit" header naming their source, and SHALL be checked in CI: `docs:generate --check` SHALL fail when the committed pages differ from a fresh generation.

#### Scenario: A validator change shows up in the docs
- **WHEN** a limit, token or DSL rule changes in the packages and `docs:generate` runs
- **THEN** the corresponding Reference page SHALL change accordingly, with no hand edit

#### Scenario: Stale generated pages fail CI
- **WHEN** a change alters a source constant without regenerating
- **THEN** `docs:generate --check` SHALL exit non-zero naming the stale page(s)

### Requirement: Documentation quality gates run in CI
CI SHALL run, for every push and pull request: `docs:generate --check`, the navigation test, Mintlify's validation (`mint validate`, which fails on warnings), its link check with anchors (`mint broken-links --check-anchors`) and its accessibility check (`mint a11y --fail-on-error`), and SHALL fail on any error or warning. Pages SHALL follow the writing standard: second person, sentence-case headings, a language tag on every code block, descriptive alt text on every image, no marketing language.

#### Scenario: A broken link or invalid page blocks the merge
- **WHEN** a pull request introduces a broken internal link or an invalid MDX page
- **THEN** the CI job SHALL fail with the offending path

### Requirement: Hosting and domain contract
The site SHALL be hosted by Mintlify from this repository via its GitHub App (access limited to this repository) with the project root set to `/docs`; the custom domain `docs.widgentic.dev` SHALL point at Mintlify by a DNS-only CNAME to `cname.mintlify.builders`, added only after its two verification TXT records (`_acme-challenge.docs`, `_cf-custom-hostname.docs`) show as verified, with TLS provisioned by Mintlify. These steps SHALL be recorded as operator steps in `TESTING.md`'s docs section (generic form) and the live DNS facts in the apps repository's runbook.

#### Scenario: The domain serves the site
- **WHEN** `https://docs.widgentic.dev/` is requested after DNS propagation
- **THEN** it SHALL answer with the documentation home page over TLS
